## T1 审批

审批请求（agent → client 的 `session/request_permission`）原文结构：

```json
{
  "sessionId": "...",
  "toolCall": {"toolCallId": "toolu_...", "title": "Running: echo hello"},
  "options": [
    {"optionId": "allow_once",   "name": "Yes",    "kind": "allow_once"},
    {"optionId": "allow_always", "name": "Always", "kind": "allow_always"},
    {"optionId": "reject_once",  "name": "No",     "kind": "reject_once"}
  ],
  "_meta": {"trustOptions": [
    {"label": "Full command",    "display": "echo hello",   "patterns": ["echo hello"]},
    {"label": "Partial command", "display": "echo hello *", "patterns": ["echo hello( .*)?"]},
    {"label": "Base command",    "display": "echo *",       "patterns": ["echo( .*)?"]}
  ]}
}
```

回复格式：`{"outcome": {"outcome": "selected", "optionId": "allow_once"}}`

要点：
1. 审批请求本身只带 `title`，**完整参数在它之前那条 `tool_call` 更新的 `rawInput` 里**（如 `{"command": "echo hello", "__tool_use_purpose": "..."}`），要按 `toolCallId` 关联。审批卡片必须用 `rawInput` 显示，不能只用 `title`。
2. 选项只有 `allow_once` / `allow_always` / `reject_once`，没有"总是拒绝"。
3. `_meta.trustOptions` 是 Kiro 扩展字段，对应终端里"信任完整命令 / 部分命令 / 基础命令"的选择。一期可以先不支持。
4. 拒绝后工具调用状态为 `failed`，内容 `User denied tool execution`，AI 回复"命令没有执行"。允许后状态 `completed`，`rawOutput` 带 stdout。

## T2 历史回放

`session/load` 耗时约 5~9 秒，返回前回放历史：`user_message_chunk`（用户消息）、`agent_message_chunk`（AI 回复）、`agent_thought_chunk`（思考）、`tool_call` / `tool_call_update`（工具调用）。顺序与原对话一致。

## T3 会话锁

对一个正被其他进程打开的会话执行 `session/load`，返回：

```
{"code": -32603, "message": "Internal error",
 "data": "Failed to start session: Session is active in another process (PID 1419646)"}
```

锁文件位于 `~/.kiro/sessions/cli/<SessionID>.lock`。服务端可以直接尝试加载，把这个错误转成"请先在终端里退出该会话"的提示，不需要自己判断冲突。

> 过程说明：这次被锁拒绝的会话 `1a185af6` 是**当前这个开发对话本身**。原因是我用 `grep "TERM-1"` 找测试会话 ID 时，当前对话的记录里也有这个字符串，结果误匹配。加载被 Kiro 的锁拒绝，没有写入任何内容。之后已给 `acp_probe.py` 加了保护：只允许加载工作目录是 `spike/workdir` 的会话，并验证了该保护对 `1a185af6` 会拒绝执行。

## T4 接管与交还（终端创建的会话 622a6bf6）

1. 终端里新建会话，发送"请只回复：TERM-1"，回复 TERM-1，退出终端。
2. ACP `session/load` 成功，回放出 TERM-1 那轮对话；发送"请只回复：ACP-OK"，回复 ACP-OK。
3. ACP 退出后，终端 `kiro-cli --resume-id 622a6bf6...` 成功，画面里依次显示 TERM-1 和 ACP-OK 两轮对话。

## T5 ACP 新建会话无法在终端续接（未解决）

ACP `session/new` 创建的会话 `164a187e`，两次用 `kiro-cli --resume-id` 续接都失败，终端报错：

```
Failed to resume session 164a187e-...: Failed to spawn kiro-cli:
kiro-cli chat _ ensure-session did not complete within 30000ms
Starting a new session instead.
```

终端会静默新开一个会话（第一次失败就是这样：在终端里发的消息落到了新会话 `473c90ad`）。

### 复查（2026-11-16 17:20）

1. 元数据对比：`164a187e`（ACP 创建）与 `622a6bf6`（终端创建）的 `.json` 结构完全一致，只有轮数、上下文占用这类正常差异。排除"ACP 创建的会话格式不同"。
2. 重新续接 `164a187e` 4 次，**4 次全部成功**，历史完整（含 ACP-OK 那轮）：第 1 次约 35 秒，后 3 次 6s / 6s / 8s。

**结论**：T5 不是"ACP 新建的会话不能交还终端"，而是终端续接偶发启动超时：`ensure-session` 有 30 秒上限，冷启动时可能超过。"冷启动慢"是推测，依据是第 1 次 35 秒、后几次 6~8 秒，没有直接证据，比如没定位到是哪个启动环节慢。

**对产品的影响**：
- App 新建的会话也可以交还终端，取消之前的限制。
- 风险点：续接超时后，终端会**静默新开会话**，用户可能以为还在原会话里。App 的"交还终端"提示里要写明：看到 `Failed to resume session` 就退出重试。
- 服务端的 `session/load` 也要设超时，超时后重试一次，避免同类问题卡住接管流程。

## 会话文件格式（待办提取用）

`~/.kiro/sessions/cli/<SessionID>.jsonl` 每行一条：`{"version":"v1","kind":"Prompt|AssistantMessage|ToolResults","data":{"message_id":...,"content":[{"kind":"text|toolUse|thinking|toolResult","data":...}]}}`。
`<SessionID>.json` 是元数据：`session_id`、`cwd`、`created_at`、`updated_at`、`title`、`session_created_reason`、`session_state`。

AI 回复文本在 `kind=AssistantMessage` 中 `content[].kind=text` 的 `data` 里，按 `message_id` 去重即可。

## 其他发现

- 终端界面（TUI）本身就是通过 `kiro-cli-chat acp` 进程驱动的（当前会话的锁持有者就是一个 acp 进程）。说明走 ACP 和终端用的是同一套后端，方向可靠。
- `session/new` 的返回带可用模式（kiro_default / kiro_planner / kiro_guide）和可用模型列表，App 里可以提供切换。
